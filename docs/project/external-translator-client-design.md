# Delphi-клиент для внешних переводчиков

Статус: архитектурный черновик, реализация не начата.

Дата фиксации: 2026-08-20.

## Назначение

Нужен офлайн-инструмент, через который координатор может выдавать человеку
ограниченное переводческое задание и безопасно принимать результат после
длительной работы. Клиент не становится второй реализацией репозитория и не
получает право напрямую менять канон или игровые архивы.

Базовая схема:

```text
repository exporter -> assignment.vnpkg -> Delphi client
Delphi client -> assignment.vnpatch -> repository importer
repository importer -> canonical JSONL -> existing LUCA release builder
```

Канонический перевод хранится в `translation/segments/*.jsonl`, а не в одном
монолитном файле. Для пользователя он может выглядеть единым проектом, но обмен
должен адресовать строки по стабильным `SEG_*` ID.

## Установленные контракты проекта

- Источник Steam/LUCA содержит японский, английский и упрощённый китайский
  слоты; русский при сборке заменяет английский слот.
- Постоянная идентичность строки задаётся `source_id`, `segment id` и
  `source_hash`, а не смещением в PAK или положением строки в файле.
- `source_hash` покрывает полную исходную запись со всеми языковыми слотами.
- Маркер `@speaker@` удаляется при экспорте источника и восстанавливается
  сборщиком. Переводчик не должен вводить его вручную.
- Внешний translation patch сейчас содержит новый текст, но не содержит
  baseline. Старый патч поэтому способен затереть более новый канон.
- `work check` выполняет текстовые и markup-проверки, а `apply-translation`
  можно вызвать отдельно. Внешний импорт обязан объединить обе стадии в одну
  транзакционную операцию.
- `database/knowledge.db` является производным индексом и не подходит как
  формат обмена.
- Агентские Markdown work packages не являются стабильным API для приложения.
- Внешнему участнику нельзя передавать полный source catalogue, `private/`,
  `private_reason` и будущие сюжетные сведения.

## Граница доверия

Рекомендуется один Delphi Project Group с раздельными программами:

| Компонент | Назначение |
|-----------|------------|
| `VNTranslator.exe` | Офлайн-редактор подписанных заданий |
| `VNCoordinator.exe` | Экспорт, dry-run импорт, конфликты и receipts |
| `VNPatchInstaller.exe` | Опциональная установка готовой игровой сборки |

Внешний клиент не получает Git, pristine-архивы, PAK-парсер, release builder,
canonical JSONL или закрытые проектные документы. Единственным писателем
канона остаётся repository-side importer.

## Пакет задания `.vnpkg`

Контейнер является ZIP с фиксированными именами и закрытой схемой:

```text
manifest.json
segments.jsonl
sources.jsonl
context.jsonl
knowledge.json
qa-rules.json
signature.ed25519
```

Manifest должен содержать:

- версии package schema и QA rules;
- `package_id`, `assignment_id`, project и source-set ID;
- роль получателя;
- дату создания и contributor ID;
- список назначенных сцен и сегментов;
- SHA-256 исходного каталога и content root hash;
- минимальную совместимую версию приложения;
- allowlist изменяемых полей и допустимых флагов;
- key ID и подпись координатора.

Для каждого редактируемого сегмента нужны:

```json
{
  "id": "SEG_S0003_R000018_G00",
  "source_id": "SRC_LUCA_E000007_R000018_G00",
  "source_hash": "sha256:...",
  "base_segment_sha256": "sha256:...",
  "speaker": "...",
  "japanese": "...",
  "english": "...",
  "chinese": "...",
  "base_translation": "...",
  "base_flags": []
}
```

Read-only context хранится отдельно и явно получает `editable: false`.
Knowledge содержит только релевантные термины, карточки, решения, открытые
вопросы и безопасные ограничения. Имена файлов и сообщения ошибок также
проходят spoiler-safe проверку.

## Патч `.vnpatch`

Патч содержит manifest и только изменённые записи:

```json
{
  "id": "SEG_S0003_R000018_G00",
  "source_hash": "sha256:...",
  "base_segment_sha256": "sha256:...",
  "translation": "...",
  "confidence": "high",
  "flags": [],
  "translator_note_safe": ""
}
```

Manifest патча фиксирует assignment/package ID, contributor ID, версию
приложения, время экспорта, локальную revision, список завершённых сцен и hash
payload. Внешний участник не задаёт канонический статус. Успешно принятый
перевод импортируется как `draft`.

## Трёхстороннее слияние

Для каждого сегмента сравниваются base, current canonical и incoming:

| Условие | Результат |
|---------|-----------|
| `current == base` | применить incoming |
| `incoming == base` | no-op |
| `current == incoming` | already applied |
| current и incoming изменены одинаково | принять |
| current и incoming изменены по-разному | ручной конфликт |
| изменился `source_hash` | блок до миграции или нового пакета |

Хэш всей сцены недостаточен: он только обнаруживает устаревание и заставляет
выбросить долгую работу. Нужен посегментный baseline. Flags нельзя молча
объединять; особенно удаление существующего флага остаётся решением
координатора.

Импорт выполняется в две фазы:

1. Полный dry-run с построением merge plan и authoritative QA.
2. Явное применение всего допустимого плана либо отказ без частичной записи.

После применения создаётся `.vnreceipt` с входными и выходными хэшами,
результатами merge, actor и временем. Клиент не удаляет локальную работу до
получения receipt.

## Локальное хранение и восстановление

Рекомендуемая платформа: Delphi 12 VCL Win64, Windows 10/11,
FireDAC + SQLite.

SQLite хранит immutable baseline, working copy и append-only edit log.
Обязательны:

- WAL;
- транзакционный autosave после короткого debounce и при смене строки;
- undo/redo между запусками;
- периодический SQLite backup;
- восстановление незавершённой сессии;
- checkpoint export по готовым сценам;
- повторный детерминированный экспорт patch revision;
- refresh package с тем же 3-way алгоритмом.

Жёсткие блокировки долгих заданий не нужны: пропавший исполнитель не должен
замораживать канон. Пересекающиеся назначения являются организационной
политикой, а не ограничением формата.

## UX переводчика

Основной экран должен показывать список сцен и прогресс, исходные слоты
JP/EN/ZH, поле русского текста, соседний контекст, говорящего, релевантные
термины, safe rules, комментарий и QA.

Нужны фильтры по незавершённым, изменённым, low-confidence, flags, notes,
ошибкам QA и конфликтам; поиск по всем доступным слотам; клавиатурная навигация;
история и diff относительно baseline.

Клиентская QA даёт раннюю обратную связь, но repository importer повторяет
авторитетные проверки. Минимальный набор:

- пустой перевод;
- потеря или добавление protected tokens;
- управляющие теги и переменные;
- запрещённый `@speaker@`;
- переносы строк и подозрительная длина;
- обязательная терминология;
- типографика, повторные пробелы и смешение алфавитов;
- flags, notes и low confidence перед экспортом.

## Reviewer mode

Добавляется после стабильного translator/import path. Reviewer создаёт
structured issues с severity, category, segment IDs, problem и suggestion, но
не меняет канон и не назначает `reviewed`. Видимость имени переводчика должна
быть отдельной политикой; технически поддерживается blind review.

## Патчинг игровых файлов

Delphi-клиент переводчика не разбирает и не пересобирает `SCRIPT.PAK`.
Repository-side coordinator после импорта запускает существующий
`game-tools/build_luca_release.py`.

Отдельный installer может проверять точные SHA-256 установленной версии,
требовать закрытую игру, делать backup, копировать готовые файлы во временные
имена, повторно проверять hashes, выполнять atomic replace и rollback.
Из-за глобальной релокации LUCA безопаснее устанавливать готовый проверенный
`SCRIPT.PAK`; binary delta допустим только для точно известного pristine hash.

## Безопасность и совместимость

Внешние контейнеры требуют защиты от path traversal, symlink, ZIP bomb,
дубликатов имён, чрезмерных размеров и неизвестных полей. Исполняемые вложения,
HTML/JS, plugins и macros запрещены. Пакеты рекомендуется подписывать Ed25519
через проверенную библиотеку, например libsodium.

Версии приложения, package schema, patch schema и QA rules независимы. Старое
поддерживаемое приложение должно уметь завершить уже открытое задание даже
после выхода новой версии.

## Этапы реализации

1. Зафиксировать закрытые схемы package, patch, receipt и conflict report.
2. Реализовать repository-side export/import и консольный dry-run 3-way merge.
3. Проверить golden fixtures: чистое применение, stale patch, конфликт,
   изменённый source hash и повреждённый контейнер.
4. Реализовать Delphi MVP: SQLite, editor, autosave/recovery, QA и checkpoint.
5. Добавить coordinator conflict UI, receipts и refresh packages.
6. Добавить reviewer mode.
7. Добавить подписи, updater/rollback и malicious-package tests.
8. Отдельно реализовать installer готовой игровой сборки.

## Решения перед реализацией

Рабочие рекомендации:

- Delphi 12 VCL Win64, Windows 10 minimum;
- показывать все три исходных языка;
- выдавать целые сцены и небольшой безопасный соседний контекст;
- по умолчанию не пересекать назначения;
- скрывать автора от reviewer до verdict;
- начать с contributor ID, персональные ключи добавить после пилота;
- не включать PAK build в внешний клиент.

Отдельно потребуется пользовательское решение о юридической политике передачи
исходного текста, модели доверия, допустимом объёме контекста, видимости
авторства и канале обновления приложения.
