# Жизненный цикл проекта перевода

## Назначение

Состояние проекта должно помогать новому агенту продолжить работу, а не
запрещать безопасные подготовительные действия. Фаза является отметкой
прогресса. Gates защищают только результаты, для которых преждевременная работа
может повредить данные или создать ложное впечатление о качестве.

Перед логическим рабочим блоком оркестратор читает состояние, запускает
`vnctl resume` и один раз проверяет операцию через `vnctl gate`. Повторять проверку
перед каждым чтением, поиском, обновлением индекса или подшагом того же блока не
нужно. Решение действует до изменения `project-status.yaml`, политики или типа
операции.

## Рабочий блок

Рабочим блоком считается законченная воспроизводимая задача:

- каталогизация исходного пакета;
- аудит одного референсного корпуса;
- пилотная сцена;
- одна логическая сцена или ограниченная очередь сцен;
- независимое ревью этой очереди;
- техническая или проверочная сборка;
- обновление знаний по уже проверенному материалу.

Агент самостоятельно выполняет все подшаги разрешённого блока, сохраняет
промежуточные результаты и останавливается только при критической ошибке или
необходимости решения пользователя.

## Фазы

- `bootstrap`: парсер, round-trip, кириллица и базовая воспроизводимость.
- `cataloguing`: полный манифест, сцены, стабильные ID, сегменты и индекс.
- `reference_preparation`: необязательный аудит внешних корпусов и калибровка
  стиля; отсутствие корпуса или фрагментов не блокирует pilot.
- `pilot`: проверка полного цикла на небольшой сцене без обязательного
  прохождения пользователем.
- `production`: последовательный или пакетный перевод и независимое ревью.
- `final_lqa`: полный игровой билд, визуальная проверка и последующее
  прохождение пользователем.

Фазы не закрывают документацию, референсы, индекс, поиск, глоссарий и
предложения в базу знаний. Они показывают достигнутый рубеж. `advance` меняет
только этот рубеж после выполнения его gates.

## Gates

Для перехода к каталогизации нужны подтверждённые извлечение, round-trip и
вывод кириллицы. Перевод конкретной сцены требует каталога, стабильных ID,
сегментации, актуального индекса и проверки защиты от спойлеров.

Технические gates относятся к активному build-профилю и его hash-pinned
исходнику. Смена `project.active_build` требует перепроверить применимость
evidence; legacy-скриншот не доказывает вывод текста в новом движке.

Созданный манифест и локальный каталог исходных записей не закрывают
`scenario_catalogued`, `stable_ids_created` или `scenes_segmented`: для этого
нужны логические сцены и нормализованные сегменты.

Технические теги, переходы и размеры интерфейса не блокируют черновой перевод.
Они блокируют сборку настоящего игрового текста или переход к финальной LQA.

Внешние референсы также не являются gate перевода. `reference_corpus_audited`
фиксирует факт выполненного аудита, но не входит в условия pilot или production.
Фаза `reference_preparation` служит отметкой прогресса и может быть пройдена без
подключённого корпуса.

`build-index`, `audit-reference-corpus`, `create-documentation`,
`modify-specifications`, `modify-glossary` и `curate-knowledge` разрешены во
всех фазах. Новые знания до подтверждения получают статус `proposed` или
`temporary`.

## Пакетный перевод

Запрещён один непрозрачный запрос, переводящий целый маршрут без контрольных
точек. Разрешён `batch-translate`: ограниченная очередь логических сцен, где
каждая сцена отдельно проходит контекст, черновик, структурную проверку,
независимое ревью и сохранение результата. Пакет не присваивает `approved` и
останавливается при критической ошибке.

## Статусы сегмента

- `todo`: перевод не начат;
- `draft`: создан машинный или человеческий черновик;
- `reviewed`: завершено независимое художественное ревью;
- `playable`: текст вошёл в успешно собранный и структурно проверенный билд;
- `lqa`: строка проверена непосредственно в игре;
- `approved`: окончательно принята после явного решения пользователя или LQA.

До первого прохождения целевой результат всего сценария — `playable`, а не
`approved`.

## Evidence и история

Допустимые статусы gate: `pending`, `in_progress`, `partial`, `passed`, `failed`
и `blocked`. Для строгой операции учитывается только `passed`.

Evidence для `passed` должно указывать на существующий воспроизводимый артефакт.
Файл должен содержательно относиться к gate; одного факта существования файла
недостаточно. Старые строки `translation/project-history.jsonl` не изменяются.

## CLI

```bash
python tools/vnctl.py resume
python tools/vnctl.py status
python tools/vnctl.py gate catalogue-sources --format yaml
python tools/vnctl.py gate batch-translate --format yaml
python tools/vnctl.py set-gate scenario_catalogued passed --evidence translation/scenes.jsonl
python tools/vnctl.py advance
```

`resume` показывает фактическое наполнение проекта, состояние индекса и
следующий рабочий блок. `gate` проверяет блок целиком. `advance` не является
разрешением на обычную работу и не требуется перед каждой сценой.

## Новая сессия

```text
прочитать AGENTS.md и project-status.yaml
→ выполнить vnctl resume
→ выбрать следующий логический блок
→ один раз проверить его через orchestrator и `vnctl gate`
→ выполнить блок до контрольной точки
→ валидировать и обновить индекс
→ записать evidence, статусы и историю
```

Пользователь может явно менять эту политику. Такое изменение фиксируется как
`policy_changed`, но не требует обхода остальных безопасных операций.
