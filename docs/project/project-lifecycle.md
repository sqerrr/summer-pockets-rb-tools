# Жизненный цикл проекта перевода

## Назначение

`vn-project-orchestrator` является обязательной точкой входа для любой работы с
парсером, каталогом, референсами, базой знаний, переводом, ревью, сборкой,
глоссарием и спецификациями. Он читает состояние, запрашивает решение
`vn-project-gatekeeper`, делегирует разрешённую работу узкому skill и после
проверки evidence обновляет состояние через CLI.

Gatekeeper ничего не изменяет. Он только проверяет фазу, обязательные gates,
политику и наличие evidence и возвращает машинно-читаемый результат.

## Фазы

Поддерживаются только шесть фаз:

- `bootstrap`: аудит репозитория, parser/builder round-trip, тестовые замены,
  проверка тегов, переходов и кириллицы; полноценные сцены запрещены.
- `cataloguing`: стабильные ID, нормализация сегментов, каталог сцен и базовый
  индекс.
- `reference_preparation`: аудит и очистка референсных корпусов; внешний перевод
  не становится эталоном автоматически.
- `pilot`: переводится ровно одна заранее выбранная пилотная сцена.
- `production`: сцены переводятся последовательно после успешного пилота.
- `final_lqa`: финальная вычитка, игровые проверки и исправления сборки.

`production_completed` является отдельным gate перехода из `production` в
`final_lqa`; его evidence должно подтверждать завершение производственного
объёма.

`python tools/vnctl.py advance` переводит проект не более чем на одну фазу и
только когда все gates текущего перехода имеют статус `passed` и существующее
evidence. Переход из `production` в `final_lqa` требует отдельного gate
`production_completed` с доказательством завершения производственного объёма;
автоматического массового перевода команда не выполняет.

## Проверочная сборка

Доказательства для gates `parser_roundtrip_verified`, `cyrillic_verified`,
`technical_tags_verified` и `layout_limits_measured` добываются только сборкой
пакета и запуском игры. Поэтому операция `verify-engine` разрешена во всех
фазах и требует единственного условия — `parser_extraction_verified`: писать
формат, который не умеешь читать, бессмысленно. Требовать здесь
`parser_roundtrip_verified` нельзя, иначе условие ссылается само на себя.

`verify-engine` покрывает тестовые строки, пересборку шрифтов, правку таблицы
несущих кодов и снятие кадров из игры. Сборка пакета с настоящим переводом
остаётся за `build-game-text` и разрешениями на перевод. Различие между ними
CLI не проверяет: это правило соблюдает оркестратор.

## Gates и evidence

Допустимые статусы gate: `pending`, `in_progress`, `partial`, `passed`, `failed`
и `blocked`. Для разрешения операции учитывается только `passed`.

Evidence для `passed` должно быть путём к существующему файлу внутри или вне
репозитория. Текстовое заявление, уверенность агента или лог без сохранённого
артефакта недостаточны. CLI повторно проверяет evidence при чтении состояния и
при `set-gate`.

Состояние хранится в `translation/project-status.yaml`. Каждое изменение gate,
фазы или вычисленного разрешения добавляется в append-only журнал
`translation/project-history.jsonl`. Старые строки журнала не редактируются и
не удаляются.

## CLI

```bash
python tools/vnctl.py status
python tools/vnctl.py gate translate-production
python tools/vnctl.py gate translate-pilot --format yaml
python tools/vnctl.py advance
python tools/vnctl.py set-gate technical_tags_verified passed --evidence docs/project/parser-audit.md
```

- `status` показывает фазу, общий статус, разрешённые операции, блокировки и
  следующую задачу.
- `gate <operation>` завершается ненулевым кодом при блокировке.
- `advance` показывает обязательный следующий шаг и при готовности фиксирует
  один переход фазы.
- `set-gate` проверяет имя, статус и evidence, обновляет состояние и дописывает
  историю.

Функция `require_operation_allowed(operation_name, root)` в `tools/vnctl.py`
является программным guard для будущих команд пилотного, производственного и
массового перевода и утверждения текста. Такие команды обязаны вызывать её до
чтения или изменения переводимых сегментов.

## Новая сессия

```text
Прочитать AGENTS.md
→ прочитать translation/project-status.yaml
→ вызвать vn-project-orchestrator
→ проверить gates через vn-project-gatekeeper
→ выполнить следующий допустимый этап
→ проверить evidence
→ обновить gate/фазу и project-history.jsonl
```

Обычная просьба продолжить работу не снимает блокировку. Пользователь может
явно изменить саму политику, но это отдельное осознанное изменение конфигурации
с валидацией и записью истории.
